## What this is
MedScribe is becoming Medioo (codename Baymax): a WhatsApp-first health-memory assistant for Bangladeshi families. A family owner (one WhatsApp number) sends photos of reports/prescriptions for one or more patient profiles (parents). The system extracts, explains in Bangla (text + voice), assigns urgency, files to a per-patient timeline, and proactively nudges the family. Full product doc: [PRODUCT.md](PRODUCT.md).

## Division of labour
- PO project (claude.ai) → writes BMX tickets with acceptance criteria; owns copy, safety rules, scope, pricing.
- Claude Code (this repo) → owns architecture, code, tests, deployment; returns a build report per ticket.
- Tanvir → final say on conflicts and the "needs Tanvir" list.

## Hard constraints (do not violate; propose instead)
1. Outbound messages never advise starting/stopping/changing a medicine or dose.
2. Urgency is never downgraded by any post-processing; when uncertain, escalate.
3. No numeric value is sent without its source crop; on low confidence, send a retake prompt, not an answer. *The crop must contain the value's text — content, not existence (DR-12): a crop that exists but shows the neighbouring words does not satisfy this.*
4. Every outbound message passes the review-gate stage (config-driven: global / per urgency / per patient; default off).
5. Real per-document cost, model, confidence and review outcome are logged. Remove the hardcoded $0.072.
6. LLM providers used only under zero-retention / no-training terms. *In force again in full: DR-6 relaxed this for a Groq evaluation run, and DR-9 dropped Groq, so the relaxation has no subject. Anthropic's API terms do not train on API inputs; confirm the retention posture before pilot week 0.*
7. Nothing in code, copy or metadata claims data is stored in Bangladesh.

## Architecture decisions already made
- Baymax is a new module (`baymax`) beside `medscribe-ai` in the same repo; the MedScribe pipeline, endpoints, UI and DB tables are left as-is. Baymax reuses `elioo-llm`, `elioo-gcp-vision`, core and CI/CD (DR-2).
- AWS Comprehend Medical (DetectEntities, SNOMED, ICD-10, RxNorm) and GCP Translate are not used in the Baymax pipeline. They are not removed from MedScribe (DR-2). Codification is out of MVP.
- Single structured LLM extraction call per document. Output schema (minimum): document_type, patient_hint, document_date, facility, values[] {name, value, unit, ref_low, ref_high, flag}, medicines[] {name, dose_text, frequency_text, duration_text}, follow_up[] {instruction, due_date}, free_text_summary, confidence {overall, per_section}.
- Extraction model (DR-10, supersedes DR-9 default; DR-9 dropped Groq): **single-tier `claude-sonnet-5` for printed documents**. Measured on the ten-document printed corpus: haiku 60.0% at $0.0118/doc with two retakes, sonnet 86.2% at $0.0253 with none; haiku's confidence sat at 0.85–0.95 on every document while its gap to sonnet ranged 0 to +0.60, so no escalation threshold recovered the gap for less than sonnet alone. `baymax.extract.vision-model` defaults to sonnet and `strong-model-threshold` to 0.0 (confidence escalation off; a `critical` flag still escalates). Haiku stays configured and unused: each tier is its own Anthropic client built from its own property (`ExtractionModelConfiguration`, wrapped in `BaymaxModelClient` so neither can displace MedScribe's `LlmClient`), so `BAYMAX_EXTRACT_VISION_MODEL=claude-haiku-4-5` plus a threshold brings the two-tier path back. Re-measure both on the handwritten batch before freezing. Groq stays in `elioo-llm` and config, unused by Baymax: its free tier caps output at 1,000 tokens/minute against the ~1,810 one document declares.
- Strong tier is `claude-sonnet-5` (DR-9; opus was ruled out on cost at $0.073–0.113/doc against a $0.15 ceiling). Extraction returns `confidence.overall`, which the metering wrapper's extractor reads into `ai_call_log.confidence`.
- Vision OCR called once per image (MedScribe currently calls it twice — Baymax must not repeat that).
- Extraction (BMX-2) lives in `com.elioo.baymax.extraction`: intake renders PDFs and non-JPEG images to JPEG pages (`PageRenderer`), Vision runs once per page keeping word geometry (`PageOcr`), one structured call goes out through `MeteredLlmClient` with the OCR text and, on a vision model, the page images. The reply is schema-validated (`extraction-schema.json`) with a single repair retry; a second failure fails the document. Below `baymax.extract.min-confidence-overall` or `min-confidence-section` the document is NEEDS_RETAKE and nothing but the document row is written. Low confidence or a `critical` flag escalates to the strong model and the more confident answer wins; `document.model_final` records which. Every item's `source_span` is mapped through Vision geometry to a bounding box and cut into `crop-{item_id}.jpg` (`CropCutter`); an item with no resolvable crop is dropped, never surfaced as a value, and `crop_key` is NOT NULL in the schema so the rule holds in the data. **Dropped items are counted, not silent**: per-section counts (`unverified_values` / `_medicines` / `_follow_up`, V6) go on the document, appear as `unverified` in the status response when non-zero, and as `unverified_items` in the weekly export. A value we could not locate is still a value the family sent, so it must show as "we could not read part of this" rather than as a shorter answer.
- The cheap tier is `claude-haiku-4-5` (`baymax.extract.vision-model`, DR-9), built as its own client in `ExtractionModelConfiguration`; a `claude-*` id builds an Anthropic client and anything else an OpenAI-compatible one, so a Groq id still works if the account is ever upgraded. Haiku 4.5 rejects both `thinking: adaptive` and `output_config.effort` with a 400, so `AnthropicLlmClient` sends neither to it — extraction is transcription and does not need them. `LlmRequest` gained an optional `images[]` and `LlmClient.supportsImages()`, both additive; MedScribe is untouched and still runs Groq by default.
- **Crops are anchored on the item's text, not on the model's offsets (BMX-5b, 2026-09-18).** A model's `source_span` offsets drift: Vision emits punctuation as separate words (`Tab . Demoprol`, `BP : 130 / 80`, `1 + 0 + 1`) and the model counts against its own de-spaced reading of that text (and sometimes the `=== page n ===` header), so offsets run tens of characters off by the bottom of a page — the last line, where the follow-up lives, fell past the end of the text and was dropped. Worse, overlap tolerance let drifted spans "resolve" to neighbouring words: replaying the ten-document corpus against fresh geometry showed **116 of the 137 crops the pipeline had stored were of the wrong words**. `CropCutter` now takes the item's own text (`SpanLocator`): the claimed words are used only if they contain it; otherwise the text is located on the page (exact nearest the claim, then fuzzy ≥ 0.8) and the whole OCR line is cropped; otherwise nothing. **Invariant: a stored crop always contains its item's text** (values: the reading, with its name on the same line — `BP : 130 / 80` gives one line crop for both readings). A crop taller than 35% of the page is refused. Replay: 137/155 → 155/155 resolved, 0 dropped; `CropCutter.Outcome` names why an item was dropped in the log, never its text. Replay harness: `RUN_SPAN_REPLAY=true SPAN_REPLAY_MANIFEST=… ./gradlew :baymax:test --tests '*SpanReplayTest*'` — Vision only, no model calls.
- **Explanation, urgency and the review gate (BMX-6, `com.elioo.baymax.outbound`).** After extraction finishes, `ExplanationService` composes the family's message. **Urgency is computed in code from the persisted extraction and nothing else** (`UrgencyService`): NOW = a value outside its *printed* range that is critical under the **STOPGAP rule (PO ruling 2026-09-18): ≥ `critical-high-multiple` × ref_high (2.0), ≤ `critical-low-multiple` × ref_low (0.5), or the page's own text marks the value critical/panic/very high/very low near it (config list, both scripts)** — the correct source is per-marker panic thresholds from a clinician, not a multiple, and that is pending, blocking week 0 — or a verbatim emergency phrase in the document text; THIS_WEEK = outside the range but not critical, a diagnosis line **on anything but a prescription**, or a follow-up already past due; ROUTINE otherwise. **Urgency reasons are evaluated against `document_type`, never in isolation** (PO ruling 2026-09-18, after the first real walkthrough parked a prescription as THIS_WEEK for `diagnosis_present`: a diagnosis on a prescription is not a reason to see a doctor — the doctor just wrote it; the same line on a lab report or discharge summary still is). Retake copy escalates per family: first retake asks for another photo, a second consecutive one says exactly what to change (light, flat, straight above), a third offers only what exists — a different document, or another try later in daylight — instead of a third attempt (`retake`, `retake.second`, `retake.third`; the human offer returns with BMX-10, when a reply can reach Tanvir); **no printed range → no escalation from values**, and the model's own `flag` is ignored. Assessment only raises, and the stored row must carry the assessed urgency or nothing is stored. The body is built from a fixed skeleton in `baymax/messages_bn.properties` (Tanvir's wife owns the wording; `messages_en.properties` mirrors it for logs) — urgency line, doctor-first line and standout lines with the extraction's own numbers — which Sonnet is asked only to phrase as plain Bangla (one `EXPLAIN` call, ≈$0.004/doc; **ROUTINE with nothing standing out is the template alone, no model call — intentional (PO, 2026-09-18), do not "fix" it**; NEEDS_RETAKE is the retake prompt alone, no facts read). Medicines never reach the skeleton or the model; **since DR-16 (2026-09-19) they enter the message only as a verbatim block appended after generation** — header `medicines.header`, then `name · dose_text · frequency_text · timing_text` exactly as stored, exempt from the phrase and number checks, verified character for character against the store or the message fails closed (`MedicineTranscription`); each line's crop is the medicine's stored crop, beside it on the document page and attached at delivery in BMX-10. Still forbidden: what a medicine is for, an inferred schedule, restated dosing, any start/stop/change advice. Then `MessageSafetyCheck` runs in code: ≤ 600 characters, every digit run in the body exists in the extraction (digits of any script folded), no medicine/dose verb from the config phrase list (whole tokens, so `ডাক্তার দেখান` does not trip on `খান`), a doctor-first marker on every NOW/THIS_WEEK body; one regeneration with the violations named, then fail closed (`outbound_message` row with no body, logged) — **and since Phase 0 PR 9 the family is then sent the code-only, value-free `explanation.fallback`** (the `UrgencyLines` block at the stored F1 level, then document type, Bangla date and the link), through the same gate and the same checklist; the model's text still never goes. A composition that throws (DR-16/DR-26: a medicine or diagnosis not verbatim, an elided dose; or the EXPLAIN model call erroring) gets the same fallback; the ERROR log carries the class and a `reason=` code, the text stays at DEBUG. When no fallback can be built the original error propagates and nothing claims a fallback went. **A document that ends FAILED gets the `failure.document` notice** (outbound kind `failure`, V23; ROUTINE; through the gate; once per document — a second `explain` finds the row and composes nothing). A failure notice does not reset the WhatsApp retake escalation (`consecutiveRetakes`: a failure is our fault, not a readable paper). The startup sweep (F9b) treats a FAILED document with no `failure` row, and a DONE one whose only explanation row is a bodyless `failed_safety`, as unanswered. `OutboundMessageGate` (DR-13) parks PENDING messages and notifies the reviewer (log until BMX-10); `POST /admin/messages/{id}/approve|reject`, `GET /admin/messages/pending`; "delivery" in v1 is the log and the timeline. `POST /documents/{id}/detail` (session) composes the longer explanation under the same rules. The newest released or approved message is rendered verbatim at the top of the document page under "সংক্ষেপে" — the only interpretive text in the UI, and it passed the checklist. V9 = `outbound_message`; the weekly export gained a `# messages` block (urgency × gate outcome).
- Images to object storage (Supabase Storage or S3), not base64 in Postgres. Done in BMX-3: `StoragePort` + `S3StorageAdapter` (`com.elioo.baymax.storage`, S3 API, private bucket, SSE header configurable), keys `{family_id}/{patient_id}/{document_id}/page-{n}.jpg` and `.../crop-{item_id}.jpg` (UUIDs only, never a phone number), ledger table `baymax.stored_object` (keys + sizes, no bytea; since D4b also each image's pixel `width_px`/`height_px`, read from the JPEG header at store time, never from the raster, both or neither and never zero (CHECK `stored_object_dimensions_whole`), with `dimensions_checked_at` saying when the size was read or found unreadable (CHECK `stored_object_dimensions_checked`: a size always has one). A crop row written before that migration has none and is measured lazily on its paper's first `GET /app/api/documents/{id}`, never when an image is served and never by a bulk job, tried once ever: a missing object, bytes that do not decode or an object over `max-file-bytes` (checked on the ledger size, before any fetch) is recorded as tried and never fetched again; page rows are not measured on read. The backfill holds at most two objects at once in the whole process, gives a fetch 2 s and the paper read 3 s, and a store that is slow or down leaves the row untried for a later read; one INFO line per read that tried anything, with counts only), signed GET URLs with a 15-minute TTL, delete-by-prefix at document/patient/family level for the 24h delete path. JPEG only: render PDFs and other formats to JPEG before `storePage`/`storeCrop`. Production is AWS S3 `elioo-baymax-prod` in ap-south-1 through the EC2 instance role (`baymax.storage.credentials=instance-role`, DR-5); MinIO is local-dev only (docker-compose, bucket `baymax`). IAM policy: `docs/aws/baymax-s3-policy.json`. Self-test from inside the container: `GET /api/v1/baymax/admin/storage/selftest` (admin token).
- Family accounts (BMX-4): `family_account` / `patient_profile` / `share_member` in schema `baymax`, reached only through `HealthRecordPort` (`com.elioo.baymax.healthrecord`, DR-1; the Postgres adapter is the only implementation, and an ArchUnit test forbids services touching repositories). Consent timestamps are set server-side and immutable (no update method, plus a DB trigger). Phone numbers exist only in those tables: keys, logs and `ai_call_log` carry UUIDs. Free tier: `baymax.free.max-patients` (1) and `baymax.free.max-docs-per-month` (3, UTC calendar month) → HTTP 402 `{reason: free_tier_patients | free_tier_documents}` via `FreeTierUseCase`; BMX-2 calls `checkCanUploadDocument` at intake. Delete-on-request is hard and inside the request: rows first, in one transaction, then the bucket once that has committed (`FamilyAccountService.deleteFamily`, and for one paper `TimelineService.deleteDocument`, below); a bucket failure after the commit is logged at ERROR with the marker `orphaned_objects` and does not fail the request; `ai_call_log` rows keep their numbers but lose the `document_id`. Endpoints under `/api/v1/baymax/families|patients`, behind the admin token until OTP (BMX-5).
- **Proactive engine (BMX-8, `com.elioo.baymax.nudge`, DR-17, DR-18).** One hourly job (`NudgeScheduler`, `baymax.nudge.cron`) evaluates five rules per patient on **stored data only — no model call in evaluation**: `follow_up_due` (open follow_up at due_date − 2 days, once per follow_up), `course_ending` (a medication whose `duration_text` parses — both scripts, bare numbers are days, weeks/months multiplied; unparseable = no nudge, logged — ends at T−1, once per medicine per prescription), `medicine_changed` (on extraction completion of a prescription with a prior one: a medicine absent now or with a different dose_text/frequency_text, named verbatim both sides; hooked in `DocumentIntakeService` after the BMX-6 message), `trend` (DR-17; distinct document dates only and the readings must span ≥ 14 days — same-day readings are one report, three inside a week is acute and already with a doctor; `baymax.nudge.trend-min-span-days`), `silence` (chronic_flags non-empty and no document in 60 days; once, then suppressed 30 days — **and at least one document ever, by ruling (PO 2026-09-19): a patient with flags who has never sent anything is an onboarding problem, not a nudge; do not "fix" this**). Every candidate becomes a `nudge` row (V10) keyed `(patient, rule, trigger)` — the dedupe key and the audit: `sent | gated | held | dropped(reason) | failed`. **Policy (DR-18, refined by DR-19)** is enforced centrally in `NudgePolicy` before anything sends: highest urgency wins and the others lose with `superseded_by_<rule>`, ties going to `NudgeRule`'s declaration order (follow_up_due > course_ending > medicine_changed > trend > silence) — **a losing date-bound rule is DEFERRED, not DROPPED (DR-20)**; caps 2 per rolling 7 days and 1 per Dhaka day (`weekly_cap` / `daily_cap`) — **a date-bound rule (follow_up_due, course_ending) that cannot go today — refused by a cap **or beaten in a tie (DR-20)** — is DEFERRED and retried the next day, expiring only when its date passes (DR-19/DR-20); it is never dropped before its date; the others drop**; outside 09:00–20:00 Asia/Dhaka a nudge is HELD to the next 09:00, never dropped; a nudge is ROUTINE or THIS_WEEK by type (`NudgeUrgency`) and by CHECK — NOW cannot be expressed. **Composition** goes through the BMX-6 path (`NudgeComposer`): a fixed skeleton from `nudge.<rule>` in `messages_bn.properties` carrying the extraction's own strings — **every message names the patient as the family entered it (`{patient}`), never "আপনার": the reader is the eldest child and the patient is their parent; dates are Bangla day-and-month (`BanglaDate`, standing rule for every outbound message including BMX-6 explanations); the trend line states the direction in words** — one model call (purpose `nudge`, so cost per nudge is `ai_call_log` filtered on purpose), the same checklist with the candidate's stored digit runs as the closed set and its verbatim strings required word for word then exempted (as DR-16), the gate — `baymax.outbound.gate-nudges=true` parks EVERY nudge PENDING during the pilot — and the same release. Every nudge ends with `nudge.optout`, a link to `/app/nudges/opt-out?p=&t=` (HMAC token, no session) that stops nudges for the patient or the whole family and confirms back; the profile page has the same switch. **Chronic flags are asked, never inferred:** a patient with none gets a card on their timeline asking once (PO option 1, 2026-09-19); the family ticks them on `/app/patients/{id}/profile` (owner only; ডায়াবেটিস, উচ্চ রক্তচাপ, কিডনি, থাইরয়েড, হৃদরোগ, free text) or at creation via the admin API; `HealthRecordPort.updateChronicFlags` is the only write and `ChronicFlagsAreAskedNeverInferredTest` proves on the bytecode that nothing in extraction, outbound, nudge, aicall or storage calls it. Manual run for ops: `POST /api/v1/baymax/admin/nudges/evaluate` (admin token). Weekly export gained `# nudges` (family × rule: sent, gated, held, deferred, dropped with reasons, failed, replied — replied reads `n/a` until BMX-10 carries replies, so the pilot log is never read as nobody answering). Out of scope here: WhatsApp delivery, pre-visit summary, voice.

  infrastructure before a family sees it: a photo sent from a phone comes back as a Bangla explanation on that
  phone. Inbound webhook (GET verification handshake, POST with `X-Hub-Signature-256` validated against the app
  secret; unsigned or mismatched → 403, logged, nothing processed), media downloaded from the Graph API and fed
  to the existing `DocumentIntakeService` path; outbound `WhatsAppMessageDelivery` behind the existing
  `MessageDeliveryPort`, **session messages only** inside the 24-hour window the family's upload opened. The
  DR-13 gate is unchanged — explanations park PENDING and only an explicit approve delivers. Login codes go out
  over WhatsApp too, as free-form session messages, never a template (DR-39, amended 2026-10-18): see the web
  bullet below. Channel entirely off when `BAYMAX_WA_ENABLED` is unset, every existing behaviour unchanged —
  that is the RUNBOOK contract. **Known: the verify token is logged in clear** — `IWebFilter` logs full request URIs
  including query strings, so every handshake writes it to the production log and Meta re-verifies periodically
  (DR-23, fix deferred; rotate the token when the filter is fixed). **Inbound idempotency (F9a, V22):** every
  inbound message is claimed in `baymax.inbound_message` before the webhook answers 200, keyed by
  `HMAC(BAYMAX_AUTH_HMAC_SECRET, "wamid:" || id)` (never the wamid, which is base64 of the number), so a Meta
  re-delivery is answered once; a claim that fails for a reason a retry can fix answers 503 (Meta retries for 7
  days), one the database refuses as data is answered unkeyed. **A known family's free text is now stored
  server-side** (a new kind of patient data at rest), as is its photos' Meta media id; an unknown sender's row keeps
  neither (CHECK) and is purged after 8 days, and text carrying a standalone six-digit run (a login code) is never
  kept. The family and patient delete paths remove the rows; a paper's delete clears its row's media id. With
  `BAYMAX_WA_ENABLED=true` the app refuses to start without `BAYMAX_AUTH_HMAC_SECRET`. Open gap (F9c, Phase 4): a
  message claimed and acknowledged, then cut off by a restart before its reply, is never answered; startup counts
  each once (WARN `never answered before this restart`, closed as `CUT_OFF`), and one Meta re-delivers is reclaimed.

  **Known phase-1 limitation — "which patient?" (deferred, not a design choice).** §1.4 is explicit that the
  account model is *one WhatsApp number → multiple patient profiles* and that **every message must be able to
  ask "Ma or Baba?"**. Phase 1 does not implement that disambiguation. A sender resolves to a family, and
  `DocumentIntakeService.accept` needs a `patientId`; today `baymax.free.max-patients=1` makes the choice
  unambiguous. **Where a family has more than one patient, phase 1 refuses the upload and replies saying Medioo
  cannot tell whose report it is — it never picks.** Picking the first would misfile one parent's report under
  the other, and every downstream artefact (timeline, trend series, nudges) would then be wrong *and internally
  consistent*. The reply reaches the sender over WhatsApp rather than only the log: a family whose photo
  vanishes in silence is the worst of the three outcomes. Phase 1 is therefore **single-patient-only by
  enforcement**, and the disambiguation conversation is core product work owed by a later phase.
- Web timeline and OTP login (BMX-5, `com.elioo.baymax.web`): `POST /api/v1/baymax/auth/request` answers 200 with one body whatever happened; since DR-39 (amended 2026-10-18, sign-in is free) it mints a code only for a number that has an account, is allowlisted and wrote to Medioo on WhatsApp within `BAYMAX_WA_SERVICE_WINDOW` (23 h), and sends it to that WhatsApp; every other number gets nothing. Otherwise the family texts "কোড" and `issueCodeFor(sender)` replies (`WaTextRouter.Route.LOGIN_CODE`). The window is `wa_last_inbound` (V17, keyed by the phone HMAC), recorded on every inbound message from an account number at Meta's send `timestamp` (clamped to now), never the receipt time. The code page says "sent" only when WhatsApp accepted the code, else shows the `wa.me` button; refusals are typed (`VerifyFailure`) on the page and one 401 on the API; `BAYMAX_AUTH_WEB_MINTS_CODE` is a laptop-only switch refused at startup with WhatsApp on; `POST /auth/verify` opens a 30-day sliding session cookie (`baymax_session`, HttpOnly + Secure + SameSite=Lax, random token stored hashed). 6-digit codes, 10-minute TTL, at most 5 codes made per number per rolling hour on both paths, counted whatever became of them (used, burned and expired all count; beyond it nothing is minted or sent), 5 wrong guesses burn the code. ## Proactive engine (v1 rules)
follow_up_due (T-2 days), medicine_changed (on new prescription diff), trend (3 consecutive readings wrong direction on configured markers), silence (chronic patient, no document ~60 days), pre_visit_summary (auto, T-1 day of follow_up).

*Corpus finding (batch 1, ten printed prescriptions, 2026-09-17):* only 1 of 10 prescriptions states a follow-up
timing, so `follow_up_due` and `pre_visit_summary` fire on ~10% of prescriptions on this corpus. **Proposed, not
built — belongs to BMX-8:** a rule named `course_ending` that derives an end date from `medicines[].duration_text`
+ `document_date` and nudges at T-1; duration text is present on most prescriptions where follow-up timing is not.

## What the evaluation corpus does and does not measure
Batch 1 (docs/testset, ten documents) is **prescriptions only**. The `values[]` score is therefore NOT a lab-report
measurement: the values on these pages are blood-pressure readings written on prescriptions. Reference ranges,
flags and trend detection are **unmeasured on real documents** until a lab-report batch exists. `follow_up` is
excluded from the headline accuracy until a corpus with follow-ups exists (1 of 10 here). Corpus expansion is
deferred — batch 2 (~10 printed lab reports) and batch 3 (~10 handwritten prescriptions) both gate pilot week 0,
not the build (PO, 2026-09-17).
