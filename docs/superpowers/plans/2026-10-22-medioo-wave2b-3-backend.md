# Medioo Web Rebuild — Wave 2b (tokens, components) and Wave 3 back end Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. In this repo each PR below runs as its own Workflow pipeline (master plan Part E): one worktree, one branch, one PR, no merge inside the pipeline.

**Goal:** Give the Wave 3 screens their visual vocabulary (one token file, the NOW red in one token, twelve components with catalog states) and every `/app/api` read and write they still lack (attention stack, timeline by month, calendar, follow-ups, the দেখেছি acknowledgement, the family settings, lab series, medicines as written), and fix the two data defects the চ্যাট and কাগজপত্র screens would otherwise show (a retake that never leaves the stack, a retake filed under a misread date).

**Architecture:**
- **Web (W2a, W2c–W2e).** `medioo-web/src/styles/medioo.tokens.json` is the one source; a TypeScript renderer turns it into the committed `tokens.css`, byte-compared on every test run. Components are React server components with one global stylesheet each, every class prefixed by the component's kebab name, so a built-CSS test can say which component uses `--now*`. The catalog route exists only in a build made with `MEDIOO_CATALOG=1`.
- **API (B3, B5, B6; E1/E2-API held for the PO).** Every route joins `AppApiRouter.mediooAppApiRoutes` behind `AppApiGuard`. Each reads through an existing use case where one exists (`AttentionUseCase` — the banner's NOW set is its `urgent` list, not a second query —, `TimelineUseCase`, `NudgeOptOutUseCase`, `FamilyAccountService`) and through one new read port per PR otherwise. Display decisions stay in Java (`PaperDisplay.kindOf`, `MarkerThreshold`'s fold, `PatientCalendar`).
- **Data (B6, D1, D2).** Three migrations besides B3's `now_ack`, each asserting its rule where every writer meets it: the OCR line a value was read from, written at extraction, for the blood-pressure pair (B6); a foreign key and a NULL-safe trigger for the retake link (D1); a generated column for the day a paper is filed under, read by every reader (D2).

**Tech Stack:**
- Spring Boot 3.4 WebFlux and R2DBC, Flyway, Testcontainers (Postgres 17, MinIO), JUnit 5, AssertJ.
- Next.js 15.5 / React 19 / TypeScript strict, Vitest, Testing Library, Playwright with `@axe-core/playwright`, stylelint, postcss.

## Global Constraints

The master plan's [Global Constraints](2026-10-21-medioo-nextjs-rebuild.md#global-constraints) and the Wave 2 plan's [Global Constraints](2026-10-21-medioo-wave2.md#global-constraints) apply **verbatim** to every task here (the `gl` alias, web commands, additive API, regenerated `app-routes.txt`, `AppApiLogSafetyTest`'s derived route list, `{"reason"}` errors, no Bangla literal outside generated files, logs, commits and staging, red replays, read-only box). `CLAUDE.md` applies too. New here, one line each:

- **No migration above V23 merges before V23 is on `origin/main`.** `BaymaxSchemaMigrator` runs Flyway with the defaults (`outOfOrder` false, `ignoreMigrationPatterns` `*:future`). A V24 applied in production before V23 makes V23 an *ignored* migration, and the next startup fails `validate`. B3, B6, D1 and D2 each check `git ls-tree origin/main baymax/src/main/resources/db/baymax/migration/ | grep -c V23__` prints `1` right before merging; if it prints `0`, stop and list it under `box_steps_pending`.
- **Migration numbers are taken at merge time** (master plan): the next free `V<n>` above V23 on `origin/main` after the final rebase. Below, a migration is named `V<n>__<name>.sql`; the PR renames the file on rebase and nothing else references the number.
- **The account holder is a `family_account`.** There is no member table. Each WhatsApp number is one `family_account`, and a share member signs in as their own `family_account`, which sees the shared patient through `share_member` (`PostgresHealthRecordAdapter.VISIBLE_SQL`). So DR-41's "member id" is `WebSession.familyId()`, the viewer's own account, never the patient's family. Decision 8's recommendation (per account holder) is therefore "per `family_account`", and a share member is a different account holder from the owner. The PO answered "per family" (DR-45 item 6). Read against this schema, that is this same per-`family_account` rule, reading (a). It is the default until the PO confirms the meaning, and B3's tables and tests below are written against it.
- **Every new table with family or patient data** has `family_id` NOT NULL (and `patient_id` where relevant) with a foreign key, is deleted explicitly in `PostgresHealthRecordAdapter.deleteFamily` and `deletePatient` and, where it has `document_id`, in `PostgresDocumentRecordAdapter.deleteDocument`. `FamilyDeletionAcceptanceTest.targets()` and `DeletionSweep.documentIdTables` find it from the schema; each of those tests' fixtures must hold a row in it before the delete (their emptiness guards fail until it does, which is intended).
- **Component styles.** One plain stylesheet per component, `src/components/<Name>/<Name>.css` (or `src/components/safety/<Name>/<Name>.css`), imported by the component. Every class selector in it starts with `.<kebab-name>` (`NowBanner` → `.now-banner`, `.now-banner__call`, `.now-banner--abroad`). No CSS Modules: the class names reaching the built CSS are the source names, so the built-CSS test reads them without guessing Next's hashing.
- **Colour literals live only in `src/styles/tokens.css`**, which is generated. Everywhere else stylelint refuses hex colours, named colours and the colour functions in CSS, and `src/lint/colour-literal.test.ts` refuses them in `src/**/*.{ts,tsx}` outside `src/styles/` (SVG `fill`/`stroke`/`stopColor` attributes and `style={}` included) (W2a).
- **The NOW and THIS_WEEK names live only in their components.** The strings `--now`, `now-banner`, `verdict-card--now` and `status-chip--crit` may appear in `src/**/*.{ts,tsx}` only under `src/components/safety/**`, `src/components/StatusChip/**`, `src/styles/` and the scanners in `src/lint/`; `--week` and `verdict-card--week` only under `src/components/safety/**`, `src/styles/` and `src/lint/` (`src/lint/now-class.test.ts`, W2a). A CSS check sees only what a selector uses; this one sees which component asks for the class. *(Amended by W2d-b, for PO sight:)* `now-banner` right after `api/` is B3's path segment (`fixtures/api/now-banner/`, `/app/api/now-banner`), not the class, and is not reported; after any other slash it still is. *(Amended by CAL / DR-48 (PR #144), for PO sight:)* MonthCalendar's own colour modifiers `month-calendar__alert--now|week` and `month-calendar__key--now|week` may appear only under `src/components/MonthCalendar/` (and `src/styles/`, `src/lint/`); MonthCalendar may not name `--now`, `--week` or another component's NOW class.
- **One filing-day rule, read, never re-derived.** From D2 on, a paper's date is `document.timeline_date` and its fallback flag `document.timeline_date_is_upload_day`, both generated by Postgres. Java maps them read-only (`Document.timelineDate()`, `timelineDateIsUploadDay()`) and every display reads them; nothing outside the entity mapping and `finish`'s write calls `docDate()` or writes `doc_date IS NULL` (D2's grep test).
- **Commit commands are given in full.** Every task's commit step is an explicit `git add <file> …` (no globs, no directories) followed by `git commit -m "<subject>" -m "Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>"`, then `git status --short -- medioo-web baymax/src scripts docs .github` showing nothing outside the list.
- **The ignore check covers every path a PR touches** (CLAUDE.md), run before the `git add`: `git status --ignored --short -- medioo-web/src medioo-web/e2e medioo-web/public medioo-web/fixtures baymax/src scripts docs .github | grep '^!!'` prints nothing, and every file the PR adds at the `medioo-web/` root (where `node_modules/` and `.next/` are rightly ignored, so the directory itself cannot be checked) is named in `git check-ignore -v <file> …`, which must print nothing.
- **New copy keys are drafts.** A key added to `baymax/src/main/resources/baymax/ui-*_{bn,en}.properties` is listed in the PR body under "Pending (PO / copy owner)", with both strings. The copy JSON is regenerated by `WebCopyExportTest` (its failure message prints the `cp` command). No component names a string that is not a key.
- **Catalog states** (`/app/catalog-test`) use only fictional data. A Bangla name a state needs (a long one, for overflow) comes from `medioo-web/fixtures/catalog/names.json`, written by a Java test, never typed in TypeScript.
- **Boards (A7).** Each W PR publishes a private screenshot board (phone 390×844, desktop 1280×800, light and dark) of its catalog states beside the matching prototype scene, listed under "Pending (PO / box)". No screenshot goes into git.

## Task D2: Retakes filed under the upload day; uncertain dates stored

Branch `fix/baymax-retake-upload-day-uncertain-dates`. Lane D. After Phase 0 PR 9 (V23) and B3. **Runs before D1**, so that D1's retake cards are dated by the rule this PR fixes.

**The defect, from the code.** `DocumentExtractionService.finish` stores `doc_date = parseDate(result.documentDate())` on every status, NEEDS_RETAKE included. A retake is a page the model could not read confidently, so its date is the least trustworthy read there is, and V20's generated `timeline_date = coalesce(doc_date, Dhaka upload day)` files the retake under it: a blurred photo sent today can sit in March 2021 on the কাগজপত্র calendar, where the family will never look. The same rule is restated in Java wherever a paper is described: `WaIntakeService.paperOf` (`d.docDate() != null ? d.docDate() : upload day`, and `newest.docDate() == null` as the fallback flag) would describe a retake on WhatsApp by its misread date, and `PaperJson.dates`, `DocumentPages.paperDateText` and the SQL readers each derive it again. Separately, the model's `document_date_uncertain` (`ExtractionResult.documentDateUncertain`) is kept only inside `extraction_json`; no column carries it, so the timeline cannot mark the date and a trend cannot drop its direction (spec §4.18).

**The fix, at the invariant** (CLAUDE.md, V13/V14): the filing day is defined once, by Postgres, and every reader reads it. No Java computes it.

## Task D1: Chat cards dated by the paper's filed day; a retake linked to the paper it replaces

Branch `fix/baymax-chat-cards-retake-link`. Lane D. After Phase 0 PR 9 (V23), B3 and **D2** are on `origin/main`: a retake card's `date` is `timeline_date`, which only after D2 is the retake's upload day; before D2 it is whatever was misread off the blurred page.

**The defect, from the code.** `PostgresTimelineReadAdapter.IN_FLIGHT` returns every RECEIVED, PROCESSING and NEEDS_RETAKE paper uploaded in the last 30 days, and `AttentionService.attention` makes each NEEDS_RETAKE one a `Retake` card. When the family sends the new photo from the retake page (`DocumentPages.sendForm`, which posts `patient` and `back` and nothing naming the old paper), the new paper is read and filed, and the old paper's retake card stays on the চ্যাট stack for up to 30 days: a stale duplicate asking for a photo the family already sent. Nothing records which paper a retake replaces. The other direction must hold while this is fixed: a NOW paper uploaded today whose printed date is months old is on the stack, because the window is the upload (`created_at >= :since`), never the printed date. Retake and reading cards carry `received_at` only; the paper's filed date (`timeline_date`) is not on them.

**Files** (main under `baymax/src/main/java/com/elioo/baymax/`, tests under `baymax/src/test/java/com/elioo/baymax/`):
- Create migration `baymax/src/main/resources/db/baymax/migration/V<n>__retake_replaces.sql` (next free number above V23 at merge):
  ```sql
  ALTER TABLE ${flyway:defaultSchema}.document
      ADD COLUMN replaces_document_id uuid NULL REFERENCES ${flyway:defaultSchema}.document (id) ON DELETE SET NULL;
  CREATE INDEX document_replaces_idx ON ${flyway:defaultSchema}.document (replaces_document_id) WHERE replaces_document_id IS NOT NULL;

The NULL pass is required, not a nicety: `ON DELETE SET NULL` is itself an `UPDATE OF replaces_document_id` to NULL, so without it deleting the original blurred paper (B4c's owner-only delete, the HTML `POST /app/documents/{id}/delete`, or a family or patient delete, all through `document` deletes) would fail with the trigger's message and answer 500.
