# MedScribe AI - Project Documentation

## Project Overview

MedScribe AI is a Spring Boot reactive application built with Clean Architecture principles for processing medical documents using AWS AI services. The application provides OCR with Bangla/English support, medical terminology extraction, medical coding, timeline visualization, voice transcription, and intelligent summarization of medical records.

## Tech Stack

### Backend
- **Framework**: Spring Boot 3.x (Reactive)
- **Language**: Java 17+ / Kotlin
- **Reactive Stack**: Spring WebFlux, Project Reactor
- **Architecture**: Clean Architecture (Hexagonal Architecture)
- **AWS Services**:
  - Amazon Textract (OCR - handwritten + printed text)
  - Amazon Comprehend Medical (Medical entity extraction + code mapping)
  - Amazon Transcribe Medical (Voice-to-text for consultations)
  - Amazon Bedrock (LLM for summarization - Claude 3 Sonnet)
  - S3 (Document storage)
  - EventBridge (Event-driven processing)

### Database & Caching
- **Primary Database**: PostgreSQL (with R2DBC for reactive support)
- **Caching**: Redis (Reactive)
- **Document Store**: MongoDB (optional, for unstructured data)

### Infrastructure
- **Build Tool**: Maven / Gradle
- **Containerization**: Docker
- **API Documentation**: SpringDoc OpenAPI (WebFlux)
- **Monitoring**: Spring Boot Actuator, Micrometer, CloudWatch

## Business Requirements & Use Cases

### 1. OCR Document Processing (FR-001)

**Owner**: TBD
**Flow**: User scans document → OCR extraction → Display formatted text

**Key Requirements**:
- **Language Support**: Bangla + English (critical requirement)
- Mobile camera capture support
- OCR processing via Amazon Textract
- Support formats: PDF, JPG, PNG (prescriptions, lab reports, radiology, discharge summaries, operation notes)
- Processing time: < 10 seconds
- Accuracy: ≥ 90%
- HIPAA-compliant secure storage/transmission

**Technology Options Evaluated**:
- AWS Textract (handwritten + printed) - **Selected**
- Google ML Kit
- Tesseract OCR
- Google Vision API/Lens
- Microsoft Azure OCR
- Donut Model

**Endpoints**:
```
POST /api/v1/documents/scan
POST /api/v1/documents/{id}/ocr
GET /api/v1/documents/{id}/text
```

**Use Cases**:
- `ProcessDocumentUseCase`: Orchestrates document upload and OCR
- `ExtractTextUseCase`: Calls Textract and formats output

**User Stories**:
- Healthcare providers: Avoid manual data entry, streamline processing
- Patients: Automatically scan documents, digitally access records without manual input

### 2. Medical Term Extraction & Coding (FR-002)

**Owner**: TBD
**Flow**: Upload document → Extract text → Identify clinical terms → Map to medical codes → Display with confidence scores → Flag low confidence for review

**Key Requirements**:
- Processing time: < 5 seconds
- Accuracy: 90% term identification, 95% code mapping precision
- Confidence threshold: < 85% requires human review
- JSON output format
- User can edit/accept suggestions

**Medical Code Systems**:
- **ICD-10**: International Classification of Diseases (diagnoses) - E11.9 (Type 2 Diabetes)
- **RxNorm**: Medication codes - 12345 (Metformin)
- **LOINC**: Laboratory test codes - 234567 (Hemoglobin)
- **SNOMED CT**: Clinical terminology - 40743004 (Stroke)
- **CPT**: Current Procedural Terminology (procedures) - 12345 (MRI Scan)

**Solution Architecture - Option B (Recommended)**:
- **Primary**: AWS Comprehend Medical for entity extraction + code mapping
- **Optional**: LLM normalizer layer for cleaning/refinement
- **Rationale**: Best balance of medical accuracy, reliability, and 1-week PoC feasibility
- **Effort**: 43-50 hours

**Alternatives Evaluated**:
- Option A: Pure Medical LLM (MedLM/GPT-4) - Fast but prone to hallucinations
- Option C: Custom LLM + Local Terminology DB - Best long-term but 114-161 hours

**PoC Note**: For initial PoC, can skip OCR steps 1-3 and directly input extracted text

**Endpoints**:
```
POST /api/v1/medical/extract-terms
POST /api/v1/medical/map-codes
PUT /api/v1/medical/terms/{id}/review
GET /api/v1/medical/documents/{id}/codes
```

**Use Cases**:
- `ExtractMedicalTermsUseCase`: Uses Comprehend Medical
- `MapMedicalCodesUseCase`: Maps terms to standard codes
- `CalculateConfidenceUseCase`: Computes confidence scores
- `ReviewLowConfidenceTermsUseCase`: Handles manual review workflow

**Response Example**:
```json
{
  "documentId": "doc-123",
  "extractedTerms": [
    {
      "term": "Hypertension",
      "category": "MEDICAL_CONDITION",
      "codes": {
        "icd10": "I10",
        "snomed": "38341003"
      },
      "confidence": 92.5,
      "requiresReview": false
    },
    {
      "term": "Chest pain",
      "category": "SYMPTOM",
      "codes": {
        "icd10": "R07.9",
        "snomed": "29857009"
      },
      "confidence": 78.3,
      "requiresReview": true
    }
  ],
  "processingTimeMs": 4200
}
```

**Owner**: TBD

**Key Requirements**:
- Chronological event ordering (newest to oldest)

**Solution Architecture - Solution 1 (Recommended)**:

**Alternatives Evaluated**:
- Solution 2: Table/Grid View (47 hrs) - Better for clinicians, dense data
- Solution 3: Card-Based View (49 hrs) - Visually engaging but space-heavy

### 4. Medical Record Summarization (FR-004)

**Owner**: TBD
**Flow**: Input unstructured records/voice → Transcribe (if audio) → Extract entities → Compute trends → Generate summaries + suggestions

**Key Requirements**:
- **Input Types**: Medical documents, raw text, AND voice audio (doctor-patient consultations, telemedicine, referrals)
- Processing time: < 5 seconds
- Accuracy: 90% in identifying key insights
- Output: Text summaries + structured JSON

**Summary Types**:
1. **Patient Summary**: 3-5 line overview (chronic conditions, recent tests, trends)
2. **SOAP Format**: Subjective, Objective, Assessment, Plan (doctor-patient visits)
3. **Referral Summary**: Doctor-to-doctor consultations condensed

**Solution Architecture - Option B (Recommended)**:
- **Voice Layer**: AWS Transcribe Medical (voice → text)
- **Extraction Layer**: AWS Comprehend Medical (entities, codes, lab values)
- **Trend Engine**: Numeric trend computation (rising/falling/stable)
- **Summarization Layer**: AWS Bedrock (Claude 3 Sonnet) for narrative summaries
- **Rationale**: Highest medical accuracy, reliable JSON output, lowest hallucination risk
- **Effort**: 70-80 hours

**Alternatives Evaluated**:
- Option A: Pure Medical LLM - Fast (52-58 hrs) but high hallucination risk
- Option C: Custom Analytics Engine - Most powerful (122-150 hrs) but not PoC-viable

## AWS Service Integration

### Amazon Textract
- **Purpose**: OCR for medical documents (FR-001)
- **Features**:
  - Printed and handwritten text extraction
  - Form data extraction
  - Table detection
  - Multi-language support (Bangla + English)
- **Configuration**: Async processing for large documents
- **Use Case**: Prescriptions, lab reports, radiology, discharge summaries, operation notes

### Amazon Comprehend Medical
- **Purpose**: Medical entity extraction and classification (FR-002)
- **Entities Detected**:
  - MEDICATION
  - MEDICAL_CONDITION
  - TEST_TREATMENT_PROCEDURE (lab tests, procedures)
  - ANATOMY
  - PROTECTED_HEALTH_INFORMATION
  - TIME_EXPRESSION
- **Code Mapping**:
  - ICD-10-CM linking
  - RxNorm linking (medications)
  - SNOMED CT linking (clinical terms)
  - Partial LOINC support (lab tests)
- **Confidence Scoring**: Provides confidence scores for entity extraction and code mapping

### Amazon Transcribe Medical
- **Purpose**: Voice-to-text transcription (FR-004)
- **Use Cases**:
  - Doctor-patient consultations
  - Telemedicine audio recordings
  - Doctor-doctor referral discussions
- **Features**:
  - Medical vocabulary optimization
  - High accuracy for clinical conversations
  - Real-time and batch processing

### Amazon Bedrock
- **Purpose**: Medical record summarization, insights generation (FR-004)
- **Model**: Claude 3 Sonnet (anthropic.claude-3-sonnet-20240229-v1:0)
- **Use Cases**:
  - Patient summaries (3-5 lines)
  - SOAP format summaries
  - Doctor-to-doctor referral summaries
  - Actionable suggestions generation
  - Grounded summarization (uses structured data from Comprehend Medical to reduce hallucinations)

### Amazon S3
- **Purpose**: Document storage
- **Buckets**:
  - `medscribe-documents-raw`: Original uploads (PDFs, images)
  - `medscribe-documents-processed`: OCR results
  - `medscribe-audio-recordings`: Voice consultation recordings
  - `medscribe-medical-reports`: Generated summaries and reports

### Amazon EventBridge
- **Purpose**: Event-driven processing
- **Events**:
  - `DocumentUploaded`
  - `OcrCompleted`
  - `VoiceTranscriptionCompleted`
  - `MedicalTermsExtracted`
  - `CodingCompleted`
  - `SummarizationCompleted`

- Support 10,000 concurrent users

### Reliability (NFR-003)
- 99.9% uptime SLA

- Graceful degradation on service failures

### Observability (NFR-004)
- Structured logging (JSON format)
- Distributed tracing (AWS X-Ray)
- Metrics (CloudWatch, Prometheus)

## Coding Standards & Best Practices

### Reactive Programming
- Use `Mono<T>` for 0-1 results
- Use `Flux<T>` for 0-N results
- Avoid blocking calls in reactive chains
- Use `subscribeOn()` and `publishOn()` appropriately
- Handle backpressure with `.onBackpressureBuffer()` or `.onBackpressureDrop()`

### Clean Architecture
- Domain layer must not depend on other layers
- Use dependency inversion (ports and adapters)
- Keep use cases focused and single-purpose
- Domain entities are anemic (no business logic in entities, use domain services)

### Exception Handling
- Use custom domain exceptions
- Global exception handler in presentation layer
- Return meaningful error messages with error codes
- Log exceptions with context

### Testing Strategy
- Unit tests for domain logic (80%+ coverage)
- Integration tests for repository layer
- Contract tests for external APIs
- End-to-end tests for critical flows

### Naming Conventions
- Use cases: `{Action}{Entity}UseCase` (e.g., `ExtractMedicalTermsUseCase`)
- Repositories: `{Entity}Repository`
- Adapters: `{Service}{Type}Adapter` (e.g., `AwsTextractAdapter`)
- DTOs: `{Entity}{Type}Dto` (e.g., `OcrResponseDto`)
